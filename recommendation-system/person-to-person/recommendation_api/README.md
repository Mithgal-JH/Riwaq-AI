## What this is

This wraps the validated logic from `person_to_person_recommendation.ipynb` (TF-IDF + Cosine Similarity, the `is_missing()` null-handling fix, the top-N ranking) as a real, deployable FastAPI service — implementing **exactly** the two endpoints locked in `BinX_PersonToPerson_Recommendation_API_Contract.docx`, field-for-field.

No part of the recommendation logic changed. This is the same model — just served over HTTP instead of run cell-by-cell.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/v1/ai/recommendations/people/sync` | Backend → AI. Pushes profile data (`full` / `upsert` / `delete`) into this service's synced index. |
| `GET` | `/api/v1/ai/recommendations/people/{profile_id}` | Returns the top-N most similar profiles, ranked by Cosine Similarity. |
| `GET` | `/health` | Liveness check — returns how many profiles are currently indexed. Not part of the contract; useful for the hosting platform's health checks. |

The AI service **never** calls back to the Backend. If a `profile_id` hasn't been synced yet, `GET` returns `404` rather than blocking on a live fetch — this is what makes the endpoint fast regardless of how many profiles exist, and avoids the N+1 pattern.

## Run it locally

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Then, in another terminal:

```bash
curl -X POST http://localhost:8000/api/v1/ai/recommendations/people/sync \
  -H "Content-Type: application/json" \
  -d '{
        "sync_type": "full",
        "profiles": [
          {"profile_id": "profile_482", "skills": ["Python","SQL"], "interests": ["Machine Learning"],
           "learning_direction": "AI & Machine Learning", "bio": "Passionate about Python and Machine Learning."},
          {"profile_id": "profile_915", "skills": ["Java"], "interests": ["Digital Marketing"],
           "learning_direction": null, "bio": "Marketing enthusiast."}
        ]
      }'

curl "http://localhost:8000/api/v1/ai/recommendations/people/profile_482?top_n=5&request_id=req_998877"
```

Interactive docs (auto-generated by FastAPI) are at `http://localhost:8000/docs`.

## Run the tests

```bash
pip install pytest httpx
pytest test_api.py -v
```

All 10 pass locally (verified before delivery): sanity-check ranking, the `learning_direction = null` case (never crashes, always reads as "not the same direction"), a near-empty profile (`low_confidence: true`, not an error), identical ("twin") profiles scoring ≈ 1.0, the full sync → upsert → delete lifecycle, and the 400/404 error paths from the contract's HTTP Errors table.

## Deploying (Render / Railway / anything Docker-based)

```bash
docker build -t binx-p2p-recsys .
docker run -p 8000:8000 binx-p2p-recsys
```

The Dockerfile reads the platform's `$PORT` environment variable automatically (both Render and Railway inject one), defaulting to `8000` for local runs — no config changes needed between platforms.

**On size/RAM:** this service holds no pretrained model file at all — the TF-IDF vectorizer is rebuilt from synced profile text on every `sync` call. Memory scales with the *similarity matrix* (`n_profiles²`), not with a model file: roughly 8 MB at 1,000 profiles, and only becomes a real concern in the tens of thousands. It fits comfortably inside a 512 MB instance at the platform's current scale.

**Not yet verified:** the Docker build itself couldn't be run in this environment (no Docker daemon available here) — the app and its logic were tested directly and pass 10/10, but please run `docker build .` once locally or in CI before the first deploy, just to confirm the image builds clean on your machine too.

## What's intentionally out of scope (per the contract's "Open Dependency")

`shared_skills` / `shared_interests` will reflect whatever fixed taxonomy the Backend team confirms for Skills/Interests/Learning Direction — this is a data question, not a contract or code change. The endpoint shape and every field name here are already final.
